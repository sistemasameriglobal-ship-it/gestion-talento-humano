RESUMEN EJECUTIVO
--------------------------------------------------------------------------------
Se ha ejecutado una inspección estática y dinámica exhaustiva de la base de código
(frontend en React 19 + Vite 8) y la capa de persistencia en PostgreSQL (Supabase).
El objetivo central es estructurar la base técnica para implementar con éxito tres
módulos críticos de gestión de talento humano:
  1. Gestión de periodos laborales y reintegros de empleados.
  2. Cálculo dinámico de antigüedad laboral por periodo contractual.
  3. Control, causación y saldo de vacaciones (días ganados, disfrutados,
     compensados en dinero y balance pendiente).

Regla de Negocio Confirmada:
"Cuando un empleado se reintegra a la empresa mediante un nuevo contrato, su
historial anterior se conserva intacto como archivo/registro histórico, pero sus
vacaciones y antigüedad para el nuevo ciclo inician desde cero en el nuevo periodo."

A continuación se detalla el diagnóstico del sistema actual, el mapa de hallazgos
y el plan técnico de implementación estructurado en las 5 secciones solicitadas.

1.2. Configuración de Supabase y Base de Datos
--------------------------------------------------------------------------------
  - Row Level Security (RLS):
    * ACTIVADO en todas las tablas (`ALTER TABLE public.<tabla> ENABLE ROW LEVEL SECURITY`).
    * Implementa funciones `SECURITY DEFINER` en PostgreSQL para evaluar accesos:
        1. `public.usuario_activo()`: Retorna TRUE si `auth.uid()` existe en
           `public.perfiles` con `activo = true`.
        2. `public.es_admin()`: Retorna TRUE si `auth.uid()` tiene `es_admin = true`.
    * Las tablas operativas (`empleados`, `novedades`, `vacaciones`, etc.) utilizan
      la política:
        `FOR ALL USING (usuario_activo()) WITH CHECK (usuario_activo())`.
    * No hay accesos públicos anónimos: toda lectura/escritura exige sesión válida
      y perfil activo.

  - Multitenancy (Arquitectura Híbrida):
    * Existe un esquema multitenancy híbrido y retrocompatible:
      a) Discriminador textual: Columna `empresa TEXT DEFAULT 'ameriglobal'`
         (valores admitidos: `'ameriglobal'` y `'global_link'`).
      b) Clave foránea relacional: Columna `empresa_id UUID REFERENCES public.empresas(id)`.
      c) Clave departamental relacional: Columna `departamento_id UUID REFERENCES public.departamentos(id)`.
    * La empresa activa se selecciona en UI mediante `CompanySwitcher.jsx`, se
      persiste en `localStorage` ('active_company') y se expone por `CompanyContext`.
    * Al consultar, las APIs filtran por `empresa = currentCompany`.
    * Al insertar/actualizar, el helper `src/api/idResolvers.js` resuelve en paralelo
      el `empresa_id` y `departamento_id` a partir del texto para poblar ambas columnas.

1.3. Manejo de Clientes Supabase y Llamadas API
--------------------------------------------------------------------------------
  - Cliente único inicializado como singleton en `src/supabaseClient.js`:
    ```javascript
    export const supabase = createClient(SUPABASE_URL, SUPABASE_ANON_KEY)
    ```
  - Regla arquitectónica del proyecto: Las vistas y componentes de UI NUNCA
    deben importar `supabase` directamente (salvo el logger de auditoría). Todas

  - Las funciones retornan la promesa generada por la API fluida de Supabase
    (`{ data, error }`), permitiendo manejo uniforme de errores y estados de carga.

2.3. Manejo Actual de Fechas, Estado y Validación de Duplicados
--------------------------------------------------------------------------------
  - El Problema del Modelo Monoperiódico Actual:
    El sistema asume que un colaborador solo tiene un único ciclo vital en la
    organización. Esto genera las siguientes fallas críticas:

    1. Destrucción de Historial al Reactivar (`toggleActivo` en `Empleados.jsx`, L202-210):
       ```javascript
       const toggleActivo = async (emp) => {
         const nuevoActivo = emp.activo === false
         const payload = nuevoActivo
           ? { activo: true, fecha_retiro: null } // ¡BORRA LA FECHA DE RETIRO ANTERIOR!
           : { activo: false, fecha_retiro: emp.fecha_retiro || hoyISO() }
         await empleadosApi.actualizarEmpleado(emp.id, payload)
       }
       ```
       Al reactivar a un empleado previamente retirado:
       * Se sobreescribe `fecha_retiro = null`, eliminando la constancia histórica
         de cuándo terminó su contrato previo.
       * No se solicita ni se registra una nueva `fecha_ingreso`, dejando la fecha
         del contrato original.
       * En `save()` (L179): `fecha_retiro: form.activo ? null : (form.fecha_retiro || null)`.
         Cualquier edición a un empleado activo elimina su fecha de retiro previa.

    2. Bloqueo por Validación de Duplicados (`checkDuplicado`, L140-150 y L164-167):
       * `checkDuplicado` normaliza cadenas (remueve tildes, diacríticos y espacios)
         y compara contra todos los empleados en `rows`.
       * Si se intenta registrar un empleado con el mismo nombre para iniciar un
         nuevo contrato, el sistema arroja:
         `"Ya existe un empleado llamado 'X'. Cambia el nombre o edita el registro existente."`
       * Si el usuario edita el registro existente, cae en la sobreescritura
         destructiva mencionada en el punto anterior.

3.2. Cálculo del Ausentismo y Validaciones de Fechas (`novedadesValidacion.js`)
--------------------------------------------------------------------------------
  - Cálculo de la Tasa de Ausentismo en el Dashboard:
    Implementado en `src/utils/dashboardStats.js` y `src/pages/Dashboard.jsx`.
    Fórmula oficial:
      Tasa Ausentismo (%) = [ Días de Ausencia / (Empleados Base × Días Calendario) ] × 100

    * Numerador: Días de novedades con conceptos de ausencia real:
      `CONCEPTOS_AUSENTISMO = ['Incapacidad', 'LNR', 'LR', '1/2 LR y 1/2 LNR',
      'Maternidad', 'Paternidad', 'Calamidad/Luto', 'Hospitalización', 'Ausente', 'Suspensión']`.
      (Se excluyen Vacaciones, Ingreso, Terminación, Retiros, Día Familia, etc.).
    * Denominador (`empleadosActivosPeriodo`, `Dashboard.jsx`, L130-148):
      Calcula qué colaboradores estaban laborando en el rango `[periodoIni, periodoFin]`:
      ```javascript
      if (e.fecha_ingreso && periodoFin && e.fecha_ingreso > periodoFin) return false
      if (e.fecha_retiro) {
        if (periodoIni && e.fecha_retiro < periodoIni) return false
      } else if (e.activo === false && periodoFin >= hoy) {
        return false
      }
      ```
    * Falla ante reintegros: Si un colaborador ingresó en 2023, se retiró en junio
      2024 y reingresó en enero 2025:
      - Si se le actualiza su única `fecha_ingreso` a enero 2025, el Dashboard
        del año 2023 lo excluye por completo (`fecha_ingreso > periodoFin`),
        adulterando retroactivamente la tasa de ausentismo de 2023.
      - Si no se le actualiza, durante los meses en que estuvo retirado (julio a
        diciembre 2024) se cuenta erróneamente como activo porque su `fecha_retiro`
        fue borrada.

  - Validaciones de Fechas en `src/utils/novedadesValidacion.js`:
    Contiene dos funciones de validación previas al guardado:

    1. `validarContraFichaEmpleado(data, fichasEmpleados)` (L6-28):
       - Bloquea novedades previas a `ficha.fecha_ingreso`:
         `"No se puede registrar una novedad con fecha X, anterior a su ingreso."`
       - Bloquea novedades posteriores a `ficha.fecha_retiro` (si `!ficha.activo`).
       - Impacto: Al reingresar un empleado con nueva fecha, si alguien edita o
         recalcula una novedad de su contrato anterior, el sistema la rechaza
         porque la fecha es "anterior a su ingreso".

    2. `validarContraHistorial(data, rows)` (L35-71):
       - Algoritmo empírico: Busca en la tabla de novedades registros donde
         `concepto === 'Ingreso'` o `'Terminación de Contrato'`.
       - Empareja cada Ingreso con la siguiente Terminación para armar tramos activos:
         `tramosActivos = [{ desde: ingresoActual, hasta: fechaTerminacion }]`.
       - Exige que cualquier novedad caiga dentro de uno de esos tramos.
       - Vulnerabilidad: El propio código documenta que estas novedades "son
         opcionales y muchas veces no se cargan". Si no se registran novedades
         explícitas de ingreso/terminación, la validación se omite; y si se
         cargan de forma incompleta, bloquea novedades válidas.

3.3. Interacción con "Ingreso", "Terminación de Contrato" y Reingreso
--------------------------------------------------------------------------------
  - En `novedadesConstants.js`, `'Ingreso'` y `'Terminación de Contrato'` son
    simples cadenas dentro del array `CONCEPTOS_LIST`.
  - En `Novedades.jsx` (L299): Se desactiva la limitación de inputs de fecha
    únicamente si `form.concepto === 'Ingreso' || form.concepto === 'Terminación de Contrato'`.
  - En `novedadesImport.js`: Importaciones con texto "No superación P. Prueba" se
    mapean a `'Terminación de Contrato'`.
  - Conclusión: Novedades no posee una estructura relacional de contratos. Utiliza
    filas de novedades como "parches" para deducir fechas, sin conexión directa
    con el ciclo contractual de la tabla `empleados`. No existe actualmente ninguna
    etiqueta o concepto formal de "Reingreso".

4.2. Cómo se Calculan o Muestran Actualmente los Días y la Antigüedad
--------------------------------------------------------------------------------
  - Cálculo de Antigüedad (`src/utils/vacacionesHelpers.js`):
    ```javascript
    export function calcAntiguedad(fechaIngreso) {
      if (!fechaIngreso) return null
      const ingreso = new Date(fechaIngreso + 'T00:00:00')
      const hoy = new Date()
      // ... resta años y meses ...
      return `${yStr}, ${mStr}` // Devuelve string: "2 años, 3 meses"
    }
    ```
    * Deficiencia de Arquitectura: Si el empleado fue reincorporado y tiene la
      fecha de ingreso original, la antigüedad cuenta todo el tiempo intermedio
      en que estuvo fuera de la empresa.
    * Hallazgo / Bug Detectado en `ModalDetalle.jsx` (L64-65):
      `calcAntiguedad` retorna un `string`, pero `ModalDetalle.jsx` asume que es
      un objeto: `{antiguedad.anios} a {antiguedad.meses} m`. Como no existen esas
      propiedades en un string, la interfaz renderiza `undefined a undefined m`.

  - Cálculo de Días Disfrutados y en Dinero:
    * Días disfrutados: Se calculan como días hábiles (`diasHabilesEntre`) entre
      `fecha_inicio` y `fecha_fin`, excluyendo domingos y festivos en Colombia.
    * Días en dinero: En `Vacaciones.jsx` (L70-76) y `ModalForm.jsx` (L248):
      `dias_en_dinero = Math.max(0, 15 - diasHabiles)`.
      Se asume una regla rígida de que cada periodo tiene exactamente 15 días
      y que cualquier saldo no tomado en tiempo se toma inmediatamente en dinero.
    * Acumulado anual (`diasAcumuladosAnio`): Solo suma los días de vacaciones
      con `fecha_inicio` en el mismo año calendario (`String(anioActual)`).

  - Ausencia Total de Causación y Saldos:
    * NO existe cálculo de días ganados (causados) en función del tiempo trabajado:
      En la legislación laboral estándar, por cada año laborado (360 días) se causan
      15 días hábiles de vacaciones ($\approx 1.25$ días por mes trabajado).
    * NO se calcula el saldo consolidado:
      $\text{Saldo Pendiente} = \text{Días Ganados} - (\text{Días Disfrutados} + \text{Días Compensados})$.
    * NO existe control de reinicio de saldo: Cuando un empleado se retira, su saldo
      debería quedar liquidado a cero. Si se reintegra, su causación debe arrancar
      estrictamente desde 0 días en la nueva fecha de ingreso contractual.

5. ARCHIVOS Y LÍNEAS AFECTADAS: PLAN DE ACCIÓN TÉCNICO

Para implementar la solución de forma limpia, retrocompatible y robusta, se define
a continuación la matriz exacta de archivos a crear y modificar:

--------------------------------------------------------------------------------
A) IMPLEMENTAR LA TABLA `empleado_periodos` Y SUS POLÍTICAS RLS
--------------------------------------------------------------------------------
1. Archivo Nuevo: `SQL/07_GESTION_PERIODOS_Y_VACACIONES.sql`
   - Creación de la tabla `public.empleado_periodos`:
     ```sql
     create table if not exists public.empleado_periodos (
       id uuid primary key default gen_random_uuid(),
       empleado_id uuid not null references public.empleados(id) on delete cascade,
       empresa_id uuid references public.empresas(id),
       empresa text not null default 'ameriglobal',
       numero_periodo integer not null default 1,
       fecha_ingreso date not null,
       fecha_retiro date,
       motivo_retiro text,
       cargo text,
       dependencia text,
       es_periodo_actual boolean not null default true,
       dias_vacaciones_ganados numeric default 0,
       dias_vacaciones_disfrutados numeric default 0,
       dias_vacaciones_dinero numeric default 0,
       dias_vacaciones_saldo numeric default 0,
       observaciones text,
       created_at timestamptz not null default now(),
       updated_at timestamptz not null default now(),
       constraint uq_empleado_periodo unique (empleado_id, numero_periodo)
     );
     ```
   - Índice único parcial para garantizar un único periodo activo por empleado:
     ```sql
     create unique index if not exists idx_empleado_un_solo_periodo_activo
     on public.empleado_periodos (empleado_id)
     where es_periodo_actual = true;
     ```
   - Políticas RLS y triggers de auditoría:
     ```sql
     alter table public.empleado_periodos enable row level security;
     create policy "empleado_periodos_acceso_usuario_activo" on public.empleado_periodos
       for all using (public.usuario_activo()) with check (public.usuario_activo());
     create trigger trg_empleado_periodos_updated_at before update on public.empleado_periodos
       for each row execute function public.update_updated_at();
     ```
   - Script de migración inicial (Seed / Backfill):
     Poblar automáticamente el periodo inicial (Periodo 1) para todos los empleados
     existentes en `public.empleados`, preservando sus fechas actuales.

2. Archivo a Modificar: `src/api/empleados.js`
   - Líneas a agregar al final (L112+):
     * `listarPeriodosEmpleado(empleadoId)`: Obtiene el historial de periodos ordenado.

--------------------------------------------------------------------------------

CONCLUSIÓN ARQUITECTÓNICA
================================================================================
La arquitectura actual del proyecto cuenta con una separación de responsabilidades
muy bien estructurada (API Layer, Contextos, UI desacoplada, RLS estricto). Sin
embargo, adolece de un acoplamiento monoperiódico en las entidades `empleados` y
`vacaciones`.

La implementación de la tabla `empleado_periodos` junto con los flujos explícitos
de "Retirar" y "Reintegrar" resuelve de manera definitiva la deuda técnica:
  1. Protege la integridad histórica de ausencias y despidos pasados.
  2. Permite reingresos limpios donde la antigüedad y las vacaciones inician
     desde cero sin borrar registros previos.
  3. Convierte el módulo de Vacaciones de un registro pasivo de solicitudes a un
     sistema activo de causación, control de saldos y compensaciones legales.
